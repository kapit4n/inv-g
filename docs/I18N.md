# Internationalization (i18n)

## Overview

Inventory Gear uses **i18next** with **react-i18next** for internationalization. Spanish (`es`) is the default language, with English (`en`) also available. The architecture supports adding new languages with minimal effort.

## Architecture

### Folder Structure

```
src/i18n/
├── config.ts          # i18next initialization and configuration
├── index.ts           # Barrel export
└── locales/
    ├── es/            # Spanish translations
    │   ├── admin.json        ├── crm.json        ├── part-finder.json
    │   ├── auth.json         ├── customers.json  ├── print.json
    │   ├── business.json     ├── dashboard.json  ├── purchases.json
    │   ├── common.json       ├── employees.json  ├── reports.json
    │   └── errors.json       ├── help.json       ├── sales.json
    │                        ├── inventory.json   ├── settings.json
    │                        ├── suppliers.json   ├── validation.json
    │                        └── vehicles.json    └── warehouse.json
    └── en/            # English translations
        ├── common.json
        ├── ...
```

### Namespaces

| `reports`      | Reports and analytics                |

| `employees`    | Employee management                  |

### Flat vs. nested keys

Locale files are **flat**: a key like `productsPage.searchPlaceholder` is the
whole string literal `"productsPage.searchPlaceholder"`, never a path into a
nested object. Because i18next is configured with `nsSeparator ===
keySeparator === "."`, `t("common.save")` redirects to the `common` namespace
only when the first segment is a registered namespace name; otherwise the whole
string is looked up — so **do not** introduce nested JSON objects or keys that
collapse into existing registered namespaces.

### Hardening & verification

The codebase was audited to remove raw keys, hardcoded English UI text (in the
Spanish locale), and missing/EN-only translations. Verification uses
`/tmp/opencode/audit-i18n.mjs` (project-aware: it parses `src/i18n/config.ts`
namespace list and the resolvable-key set per namespace):

- 0 keys missing in `es`
- 0 keys missing in `en`
- 0 keys present in `en` but missing in `es` (English fallback leak)
- 0 `t('key', 'english default')` fallback calls in source

Accepted remaining hardcoded English: proper nouns and technical terms
(`Inventory Gear`, `USB`, `Bluetooth`, `Network`, `Letter`), plus Spanish
strings baked into a legacy `data-table.tsx`. Demo/sample data shown in empty
table placeholders is intentionally left untranslated.

## Usage

### In React Components

```tsx
import { useTranslation } from "react-i18next"

function MyComponent() {
  const { t } = useTranslation()

  return <h1>{t("dashboard.title")}</h1>
}
```

### With a Specific Namespace

```tsx
const { t } = useTranslation("inventory")

// Now all keys are scoped to inventory namespace
t("addProduct")       // instead of t("inventory.addProduct")
```

### With Interpolation

```json
{
  "itemsCount": "{count} items"
}
```

```tsx
t("purchases.itemsCount", { count: 12 })
```

### With Pluralization

```json
{
  "item": "item",
  "item_plural": "items",
  "item_count": "{count} item",
  "item_count_plural": "{count} items"
}
```

## Adding a New Language

1. Create a new folder under `src/i18n/locales/` (e.g., `fr/`)
2. Copy all JSON files from `es/` and translate the values
3. Register the language in `src/i18n/config.ts`:

```typescript
import frCommon from "./locales/fr/common.json"
// ... import all files

const resources = {
  es: { /* existing */ },
  en: { /* existing */ },
  fr: {
    common: frCommon,
    // ... all namespaces
  },
}
```

4. Add the language option in the Settings page

## Language Detection Priority

1. **Saved preference** — persisted in localStorage via Zustand
2. **Spanish** — default fallback

## Naming Conventions

- **Dot notation**: `feature.key.subkey` (e.g., `inventory.addProduct`)
- **Descriptive keys**: Use meaningful names, not generic labels
- **No abbreviations**: `dashboard.recentActivity` not `dash.ra`
- **Consistent casing**: camelCase for compound keys

## Best Practices

1. **Always use `t()`** — never hardcode user-facing strings
2. **Keep translations in the correct namespace** — `common` for reusable labels, feature namespaces for specific content
3. **Use interpolation for dynamic values** — don't concatenate translated strings
4. **Group related keys** — use nested objects for logical grouping
5. **One key per concept** — avoid duplicating translations for the same concept

## Formatting

The application uses the browser's `Intl` API for formatting dates, numbers, and currency, which automatically adapts to the user's locale when a language is selected. This is configured per feature in the respective translation files.
